
## 云效与日常发布

GitHub PR及main推送的`static-site-checks`检查负责类型、Lint、静态构建及安全检查器测试，不接触生产凭据。`main`禁止强推和删除；单人维护不要求额外审批人。已有Linux CI成功记录，后续修改仍需重新通过检查。

云效使用公共Git源，Webhook仅匹配main push，源码拉取不需要GitHub长期令牌。构建在云效公共香港构建机完成，不在2GiB ECS上安装依赖或编译官网。`deploy/ci-build.sh`准备经SHA-256核验的固定Node版本，执行`npm ci`和`npm run ci:verify`；构建失败不得进入发布。

`deploy/ci-publish.sh`只打包`dist/client/`，用临时权限600的CI密钥文件，经校验主机指纹的SSH连接向`01yang-deploy`发送`publish`，制品从标准输入流式传输。临时密钥与压缩文件在步骤退出时清理；不传源码、node_modules、服务端构建产物或运维配置。

服务器只由管理员通过`bootstrap.sh`安装root所有、部署用户只读的`receive-release.sh`、`release.sh`和校验器。CI强制命令入口接收制品后调用`release.sh`；人工运维密钥仍以`01yang-deploy`运行受控发布工具。TLS和初始化需要管理员，日常发布无通用sudo权限。

制品根目录必须包含`index.html`、`index.rsc`、`404.html`、robots、sitemap、静态资源、`version.json`和`SHA256SUMS`；版本文件记录完整Git SHA及UTC构建时间。成功发布的原始压缩包与SHA-256文件保存在ECS的`shared/archives/`，不是云效内置制品库。当前公共`ArtifactUpload` schema不可用，本方案不购买制品服务，也不依赖该步骤。

YAML在`deploy/aliyun-flow.yml`维护；提交文件不会自动同步云效配置。仅在需要变更流水线时，通过短期写凭据运行`node scripts/ops.mjs sync`并核对远端保存结果，随后撤销临时凭据。当前方案不使用VMDeploy、不安装或注册旧Runner、不创建新服务连接。旧手动Runner不能安全复用；探索期间建立的空主机组不作为发布依赖，清理状态见交付记录。

私密变量组在控制台单独关联：编辑官网流水线 → 变量和缓存 → 通用变量组 → 关联`01yang-company-website-prod-secrets`（OpenAPI ID `43787`）。当前中心站YAML校验不接受该数字API ID，因此不将它直接填入`variableGroups`；更新YAML后仍需复核此关联。已验证本项目的配置同步不会移除该关联。加密变量名为`COMPANY_DEPLOY_SSH_KEY`，只关联官网流水线`5230708`；流水线分组为“零一扬公司官网”（`150804`）。

流水线串行发布，并由服务器独立锁二次保护。首次人工运行并验收后才接入GitHub Webhook，至少用一次真实main提交验证自动触发，成功/失败通知也必须实际验证；仅有YAML、Webhook或通知配置不算验收通过。

发布顺序：获得独立锁 → 检查旧站 → 安全解包和完整校验 → 原子切换current → 检查官网版本、首页、关键资源和旧站 → 原子保存并校验归档 → 记录成功。保留最近5个成功版本，current/previous引用的版本额外保护；对应旧归档及其校验文件一起清理，`shared/static/`不自动删除。中断或验收失败时恢复官网上一指针；SIGKILL/断电无法依靠进程trap处理，需按人工回滚步骤恢复。

## 回滚、排查与恢复

使用人工运维密钥连接，以官网部署用户执行；CI密钥不能运行回滚命令：

```bash
/usr/local/lib/01yang-company-website/release.sh --rollback <已成功的版本ID>
```

回滚重新校验目标文件并执行双站健康检查；失败时恢复回滚前指针。没有活动版本的首次预部署失败，会恢复无活动版本状态并继续维护态。

- 校验失败：不忽略错误、不直接解包覆盖current；从对应CI提交重新生成可信制品。
- 构建失败：查看云效或GitHub检查，旧版本不应改变。
- 官网503：先核对备案门槛和开放开关，不能直接认定发布失败。
- HTTPS异常：检查官网证书有效期、独立定时器和错误日志，不重置全站证书。
- 失败版本与下载文件：确认不被current/previous引用、没有发布运行后，才清理官网目录内的明确目标；不清空shared/static，不跨项目递归删除。
- 服务器恢复：重新初始化官网资源，从已验证的ECS制品归档、其加密备份或对应Git提交恢复；详细顺序见下一节。不要假设云效存在可下载的历史制品。

## 凭据轮换与加密备份

### 轮换顺序

- 五年只读PAT：新建官网专属、仅含同样读取权限的令牌，记录名称和精确到期时间；在权限600的私有配置中替换后验证`ops:status`、`ops:runs`，再撤销旧令牌并更新加密备份。不要靠扩权解决读取失败。
- CI SSH密钥：生成新官网专用密钥，先把新公钥以相同`restrict,command="/usr/local/lib/01yang-company-website/receive-release.sh"`限制追加到官网用户授权文件，保留旧钥；更新云效加密变量及`OPS_CI_SSH_KEY_FILE`路径索引，实际验证发布和“非publish命令被拒绝”，成功后精确移除旧公钥行、旧变量值和过期私钥副本。不覆盖整个`authorized_keys`，不删除人工运维钥。
- 人工运维SSH密钥：先追加带`restrict`的新公钥，使用第二个连接验证能以`01yang-deploy`执行所需运维，更新`OPS_SSH_KEY_FILE`再精确移除旧钥。保留已验证连接直到完成，不修改25th授权。
- 私有Webhook：重新生成后先更新GitHub触发配置和私有索引，验证一条真实main提交只触发官网流水线，再使旧地址失效。初始化写令牌在配置验收完成后撤销；撤销结果与无本地残留都应确认。
- SSH服务器指纹：主机迁移或密钥变更时，从可信管理员通道核对新公钥后更新`deploy/known_hosts`，经PR和CI验证。不能为了通过发布而关闭严格校验，或把未经核对的网络扫描结果直接当成可信指纹。
